# Observability Standard — Sery Backend

## 1. Objective

Define logging, tracing, and health monitoring standards for the Sery backend to ensure:

- Traceability of requests
- Structured error diagnostics
- Production debugging capability
- A clean base to add distributed tracing later

---

## 2. Logging

### 2.1 Standard

All logs must be structured and include, when available:

- `service`: service name (e.g. `sery-api`)
- `env`: environment (`Development`, `Staging`, `Production`)
- `requestId`: correlation ID (`X-Correlation-ID`)
- `userId`: resolved user id (when authentication exists)
- `route`: endpoint path
- `method`: HTTP method
- `statusCode`: HTTP status code
- `elapsedMs`: request duration in milliseconds
- `errorCode`: internal error code from `ErrorCatalog` (for failures)
- `messageKey`: localization key from `ErrorCatalog` (for failures)

### 2.2 Correlation

- Every HTTP request must carry `X-Correlation-ID`.
- If the header is missing, it is generated by `RequestContextLoggingMiddleware`.
- The correlation id must be propagated to:
    - Logs (via log scopes / enrichment).
    - Responses (header `X-Correlation-ID`).
    - Downstream services when added in the future.

### 2.3 Error Logging

All unhandled exceptions must be logged with:

- `requestId`
- `errorCode` (when mapped in `ErrorCatalog`)
- `messageKey`
- stack trace (only in secured logs; never in API responses)

`GlobalExceptionMiddleware` is responsible for this behavior.

---

## 3. Logging Stack

Initial implementation:

- **Serilog** as the logging pipeline.
- Console sink for all environments (JSON or structured text).

Allowed future sinks:

- Seq (local debugging).
- Cloud logging (e.g. Azure Application Insights, Datadog, Grafana Loki).

Configuration must keep the same structured fields described above.

---

## 4. Health Checks

### 4.1 Endpoints

- `/health/live`
    - Returns 200 when the API process is running.

- `/health/ready`
    - Intended to check readiness of dependencies:
    - Database (PostgreSQL).
    - Cache (Redis).
    - For the MVP, this may just mirror liveness until dependencies exist.

### 4.2 Response Format

Standard JSON when using ASP.NET Core health checks:

```json
{
    "status": "Healthy",
    "checks": [
        {
            "name": "self",
            "status": "Healthy",
            "duration": "5ms"
        }
    ]
}
```

---

## 5. Metrics (Phase 1)

Phase 1 metrics are **log-derived**:

- Count of total requests.
- Count of 4xx and 5xx.
- Errors grouped by `errorCode`.

External aggregation is out of scope for the MVP, but logs must contain sufficient structured data to support it.

---

## 6. Future: OpenTelemetry

Planned, but not part of the MVP:

- Distributed tracing (end-to-end request traces).
- Metrics export (latency, error rate, throughput).
- OTLP export to a backend (Grafana, Azure Monitor, etc.).

---

## 7. Observability Backlog

- External log aggregation (Seq / Application Insights / other).
- Database health check for PostgreSQL.
- Redis health check.
- OpenTelemetry tracing (HTTP + DB).
- Metrics dashboards for:
    - Request rate.
    - Error rate by `errorCode`.
    - Latency per route.

---

## 8. Principles

- No unstructured logs.
- No silent failures.
- Every error must be traceable via `requestId` (correlation id).
- Observability must never leak sensitive data (tokens, passwords, PII).
